## Findings

### 1. Shared loading skeletons are not announced to assistive technology

- Status: OPEN
- Priority: HIGH
- Area: shared feedback and data-table state
- Rules: R-27, C-4; current Vercel async-update and semantic-HTML guidance
- Evidence:
  - `console/src/components/feedback/loading-state.tsx:3-9` renders only
    skeleton rectangles inside a generic `div` with `aria-label="Loading"`
    and `aria-busy="true"`. It has no status role, live region, or accessible
    loading text.
  - The shared component is imported by 42 Console source files, including
    the Admin, project, account, storage, database, and public status views.
  - `console/src/components/data-table.tsx:80-146` renders another visual-only
    skeleton state. Its wrapper has `aria-busy`, but no loading announcement or
    status text while rows are being fetched.
- Minimal proof path: navigate to a view while its first query is pending and
  inspect the accessibility tree with a screen reader. The visual page shows
  grey skeleton rows, but the generic `div` does not expose a meaningful
  status announcement. The same issue occurs while a table refresh is in
  progress.
- Impact: a screen-reader user can experience a blank or unchanged region and
  cannot tell whether the page is loading, stalled, or empty. Because this is
  a shared primitive, the issue repeats across many control-plane screens.
- Recommended remediation: preserve the skeleton visuals but add one bounded,
  non-spammy `role="status"`/`aria-live="polite"` announcement with visible or
  visually-hidden text such as `Loading...`; give the shared table loading
  path equivalent semantics. Do not announce each skeleton row separately.
- Recommended regression test: render `LoadingState` and a loading
  `DataTable`, then assert a status/live-region node with the loading message
  exists and that the skeleton cells are not individually exposed as status
  messages.

### 2. ECharts telemetry charts expose no usable data alternative

- Status: OPEN
- Priority: MEDIUM
- Area: Admin telemetry visualization
- Rules: R-27, R-32, C-4; meaningful-media and semantic-HTML guidance
- Evidence:
  - `console/src/features/admin/admin-log-volume-chart.tsx:29-30` creates a
    canvas-rendered ECharts instance, while `:72` returns only a generic
    `div` with `aria-label="Log volume"`.
  - `console/src/features/admin/admin-metric-chart.tsx:49` also uses the
    canvas renderer, while `:127-132` returns only a generic `div` with
    `aria-label="Metric time series"`. No chart description, accessible data
    summary, or ECharts accessibility configuration is present.
  - `console/src/features/admin/admin-errors-view.tsx:81-89` presents log
    volume only as the chart; its error-group table does not expose the bucket
    timestamps and counts represented by the chart.
  - `console/src/features/admin/admin-dashboards-view.tsx:524-526` can render
    the metric chart as a saved dashboard panel without the metrics-page table
    that exists at `admin-metrics-view.tsx:83-121`.
- Minimal proof path: open Admin Errors or a dashboard containing a metric
  panel with a screen reader or with canvas content unavailable. The region is
  named only by a generic label and the underlying time-series or volume
  values are not available as navigable text.
- Impact: operators who cannot perceive the canvas lose telemetry data needed
  to identify volume spikes or metric trends. The main metrics page partly
  mitigates this with a table, but the log-volume and dashboard contexts do
  not.
- Recommended remediation: provide a concise, dynamic textual summary and a
  keyboard-accessible data table or equivalent disclosure for every chart
  context. Give each chart a meaningful name tied to its metric and time
  range; do not expose arbitrary raw chart internals.
- Recommended regression test: render each chart with representative points
  and assert a semantic chart description plus an accessible summary/table
  containing the same timestamps, series, and values.

### 3. Two Admin actions remain below the 44 px touch target

- Status: OPEN
- Priority: HIGH
- Area: Admin audit and trace actions
- Rule: R-03
- Evidence:
  - `console/src/features/admin/admin-audit-view.tsx:82-88` renders
    `Load older activity` as a raw button with only `text-xs` styling and no
    padding or minimum height. Its hit box is approximately its text line
    height.
  - `console/src/features/admin/admin-traces-view.tsx:124-136` wraps a small
    trace-ID badge in a raw button with no `min-h-11`, padding, or minimum
    width. The button's target is approximately the badge dimensions.
  - The shared `Button` primitive correctly uses `min-h-11` in
    `console/src/components/ui/button.tsx:21-26`, so these raw buttons bypass
    the Console's established target-size contract.
- Minimal proof path: use the Admin Audit or Admin Traces screen on a touch
  viewport and measure or tap the two controls. Both are substantially smaller
  than 44 by 44 CSS pixels and require precision tapping.
- Impact: mobile operators can miss the pagination or trace-detail action,
  especially when controls are adjacent to dense operational data.
- Recommended remediation: retain the compact text/badge visual treatment but
  give each button a 44 px hit box with `min-h-11` and appropriate horizontal
  padding. Keep visible spacing between adjacent targets.
- Recommended regression test: add a component or browser test that asserts
  the computed minimum height of both actions and verifies activation still
  updates pagination or opens the trace detail.

### 4. Live-tail connection failures are not announced

- Status: OPEN
- Priority: MEDIUM
- Area: Admin live log tail
- Rules: R-27, C-4; current Vercel async-update guidance
- Evidence:
  - `console/src/features/admin/admin-logs-view.tsx:118-128` renders the
    dynamic `Connecting to live stream`, `Streaming new records`, and
    `tail.error` messages in a plain `div` and `span` tree.
  - The region has no `role="status"`, `aria-live`, or alert semantics. The
    underlying hook reports the concrete failure text at
    `console/src/api/queries/observability.ts:86-89`, but it is only visually
    rendered by the Admin view.
  - The separate `LogViewer` already uses `aria-live="polite"` at
    `console/src/components/log-viewer/log-viewer.tsx:152-185`; the Admin
    live-tail status strip does not.
- Minimal proof path: enable Live tail, disconnect the event stream, and
  observe that the status changes and error are visible but are not announced
  when focus remains elsewhere on the page.
- Impact: an operator using a screen reader can continue believing that live
  data is streaming after the connection has failed, which is especially
  misleading in an incident workflow.
- Recommended remediation: expose the connection state through one polite
  status live region and announce a transition to failure once. Avoid nesting
  duplicate alert and status regions that repeat the same error.
- Recommended regression test: mock the stream from connecting to connected
  to failure and assert the live-region text changes to the retrying/error
  message without duplicate announcements.

### 5. Saved dashboard telemetry panels have a non-actionable error state

- Status: OPEN
- Priority: MEDIUM
- Area: Admin dashboards and telemetry degradation
- Rules: R-27 and C-4
- Evidence:
  - `console/src/features/admin/admin-dashboards-view.tsx:514-531` reduces a
    failed metric query to the plain text `Telemetry unavailable.` with no
    retry control or live-region semantics.
  - `:545-577` does the same for log panels, and `:587-616` does it for
    monitor-status panels.
  - The same product has a retryable shared error surface in
    `console/src/components/feedback/error-state.tsx:39-52`, and the full-page
    Admin telemetry views use it. The saved-panel path does not provide the
    same recovery action.
  - A dashboard can set `refreshInterval` to `false`; in that state a failed
    query has no panel-local retry action and no scheduled recovery attempt.
- Minimal proof path: open a saved dashboard with refresh disabled, make the
  telemetry request fail, and inspect the panel. It displays only
  `Telemetry unavailable.`; the operator cannot retry from the affected panel
  and a screen reader is not notified of the state transition.
- Impact: dashboards used for operations can silently degrade into stale or
  unavailable panels without telling the operator how to recover. This is a
  control-plane state problem, not just a copy issue.
- Recommended remediation: give each failed panel a compact but explicit
  error state with `role="alert"` or an appropriate polite status, a retry
  action, and a message that names the affected panel. Preserve the existing
  polling behavior when it is enabled.
- Recommended regression test: render metric, log, and monitor panels with a
  failed query and `refreshInterval={false}`; assert an announced error and a
  working retry action for each panel.
