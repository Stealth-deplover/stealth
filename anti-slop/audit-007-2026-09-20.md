## Findings

### 1. Organization loading cards bypass the shared loading announcement

- Status: OPEN
- Priority: HIGH
- Area: organization collection loading state
- Rules: R-27, C-4; human skill missing-state guidance
- Evidence:
  - `console/src/features/organization/organizations-view.tsx:67-78`
    renders three animated placeholder cards directly when
    `query.isLoading` is true.
  - Unlike the shared `LoadingState`, this region has no `role="status"`,
    `aria-live`, `aria-busy`, or loading text.
  - The same view already uses `ErrorState` for failures and `EmptyState` for
    the zero-organization case, so only this loading branch bypasses the
    shared state contract.
- Minimal proof path: open the organization switcher landing route on a slow
  connection or reload it while the organizations query is pending. A sighted
  user sees pulsing cards, while a screen-reader user receives no bounded
  loading announcement.
- Impact: the page can appear silent or unchanged while the workspace list is
  being fetched. This is especially confusing before the user can reach the
  project console.
- Recommended remediation: keep the existing card geometry but wrap it in
  `LoadingState` with a contextual label such as `Loading organizations…`, or
  add equivalent status semantics without creating one announcement per
  skeleton.
- Recommended regression test: render `OrganizationsIndexView` with a
  pending organizations query and assert one status/live region with a
  contextual loading label and no duplicate skeleton announcements.

### 2. Several secondary query failures are visible but not announced

- Status: OPEN
- Priority: HIGH
- Area: asynchronous Admin and Agent data states
- Rules: R-27, C-4; current Vercel async-update guidance
- Evidence:
  - `console/src/features/admin/admin-overview-view.tsx:240-242` renders
    `Telemetry sources unavailable.` as an ordinary paragraph when the
    sources query fails.
  - `console/src/features/admin/admin-status-page-view.tsx:240-242` renders
    `Incident list unavailable.` as an ordinary paragraph when the incidents
    query fails.
  - `console/src/features/agents/agents-view.tsx:427-430` renders the agent
    runs query failure as an ordinary paragraph, despite the surrounding
    application using `ErrorState` and `role="alert"` for comparable query
    failures.
  - These branches do not add a local `role="alert"` or live region. The
    browser setup account/domain messages were not counted here because their
    active setup section already provides an `aria-live` region.
- Minimal proof path: keep the relevant page open and reject the secondary
  request after the initial shell is rendered. The text appears visually,
  but no bounded status update is guaranteed for assistive technology.
- Impact: users may miss that one panel is stale or unavailable while the rest
  of the page remains usable. This can lead to decisions based on incomplete
  operational data.
- Recommended remediation: use the shared `ErrorState` where a retry is
  appropriate, or add a small reusable inline error presenter with
  `role="alert"`, explicit context, and a retry action when one is safe.
- Recommended regression test: reject each secondary query and assert the
  rendered error is exposed through an alert/live region without duplicating
  the message on every poll.

### 3. Browser setup field errors are not associated with their controls

- Status: OPEN
- Priority: MEDIUM
- Area: first-run browser setup forms
- Rules: C-4; current Vercel form and field-error guidance
- Evidence:
  - `console/src/features/auth/browser-setup-view.tsx:42-44` renders
    `fieldError` as a bare paragraph with no stable `id`.
  - `console/src/features/auth/browser-setup-view.tsx:170-189` gives the
    shared setup `Field` a label and `htmlFor`, but does not connect its error
    output to the child control.
  - Representative controls at `:675-694` and `:801-834` render validation
    messages without `aria-invalid` and `aria-describedby` references.
  - The global setup `aria-live` region can announce broad setup notices, but
    it does not identify which individual input is invalid when several
    fields fail validation.
- Minimal proof path: submit the Instance or manual GitHub stage with an
  invalid value, then inspect the accessibility tree or navigate by keyboard.
  The error is visible below the field, but the focused input has no invalid
  state or programmatic description.
- Impact: screen-reader and speech-input users cannot reliably associate the
  validation message with the field that needs correction, especially in the
  multi-field setup stages.
- Recommended remediation: give each field error a stable id, pass the error
  metadata through the `Field` helper, and set `aria-invalid` plus
  `aria-describedby` on the affected input or select. Preserve the current
  visible messages and setup flow.
- Recommended regression test: render representative setup fields with
  validation errors and assert the invalid control references the matching
  error node.

### 4. Incident detail rows use a focusable table row as an action

- Status: OPEN
- Priority: MEDIUM
- Area: Admin incident list interaction semantics
- Rules: R-26, R-32; current Vercel semantic HTML guidance
- Evidence:
  - `console/src/features/admin/admin-incidents-view.tsx:86-96` attaches
    `onClick`, `tabIndex={0}`, and an Enter/Space handler directly to a
    `<tr>`.
  - The row has a visible focus style, but it has no button/link role or
    accessible action name. A table row is still announced as row content, not
    as an activatable control.
- Minimal proof path: navigate the incident table with a screen reader and
  keyboard. The row can receive focus and open the detail panel, but the
  control semantics do not communicate that action consistently across
  assistive technologies.
- Impact: keyboard users can activate the row, but users relying on semantic
  navigation may not discover that the row opens incident details. The
  interaction also depends on custom key handling instead of native button or
  link behavior.
- Recommended remediation: keep the table structure and move the action to a
  real button or link inside the incident cell, or provide a carefully named
  semantic control while leaving the row itself non-interactive.
- Recommended regression test: assert the incident detail action is exposed
  as a button or link, supports Enter/Space natively, and still opens the same
  detail panel.

### 5. Organization audit uses a generic empty-table message

- Status: OPEN
- Priority: LOW
- Area: organization audit empty state
- Rules: R-27, C-3; UI skill empty-state guidance
- Evidence:
  - `console/src/components/data-table.tsx:59` defaults empty tables to
    `No records yet.`.
  - `console/src/features/organization/audit-view.tsx:36-70` renders the
    shared table without an `empty` override, so an organization with no
    audit events receives the generic message.
  - The page has enough context to say what is empty, but the message does
    not distinguish an empty audit history from an unavailable query or a
    filtered result.
- Minimal proof path: open Organization -> Audit for a new organization with
  no events. The table shows the generic fallback without a contextual next
  step.
- Impact: users cannot immediately tell whether the organization has never
  emitted an event or whether the table is still waiting for data. This is a
  low-severity clarity issue because loading and error states exist.
- Recommended remediation: pass a contextual empty message such as
  `No audit events recorded for this organization.` or use a domain-specific
  empty component if a next action is useful.
- Recommended regression test: render the audit view with an empty event page
  and assert the domain-specific message is shown.
