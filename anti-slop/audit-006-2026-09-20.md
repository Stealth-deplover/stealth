## Findings

### 1. Several route and shell loading fallbacks are still visual-only

- Status: OPEN
- Priority: HIGH
- Area: route loading, authenticated shell loading, and Services canvas
- Rules: R-27, C-4; current Vercel async-update and semantic-HTML guidance
- Evidence:
  - `console/src/components/layout/console-shell.tsx:44-52` renders the
    pending account state as three `Skeleton` rectangles without a
    `role="status"`, live region, or accessible loading text.
  - The expired-session branch at
    `console/src/components/layout/console-shell.tsx:54-63` also starts with
    a visual skeleton and exposes the redirect message only as an ordinary
    paragraph.
  - The Suspense fallbacks in
    `console/src/app/(auth)/accept-invitation/page.tsx:7-9`, `login/page.tsx`,
    `recovery/page.tsx`, `register/page.tsx`, `reset-password/page.tsx`,
    `setup/page.tsx`, `verify-email/page.tsx`, and `verify/page.tsx` each
    render a bare `Skeleton` at the fallback boundary.
  - `console/src/features/services/services-canvas-loader.tsx:12-15` uses a
    bare skeleton as the dynamic-import loading fallback.
  - The shared `LoadingState` and `DataTable` loading paths were correctly
    fixed by the previous audit follow-up, but these independent fallbacks
    bypass those semantics.
- Minimal proof path: navigate directly to an auth route, reload while the
  account query is pending, or open Services while the canvas chunk is being
  loaded. A sighted user sees a placeholder, but a screen-reader user is not
  given a bounded loading status.
- Impact: users can experience a blank-looking or unchanged region with no
  indication that navigation/data loading is in progress. This is especially
  misleading during session expiry, where a redirect is also underway.
- Recommended remediation: retain the existing visual skeletons but wrap
  each fallback in one non-spammy `role="status"`/`aria-live="polite"`
  region with `Loading…` or an equivalent context-specific announcement.
  The expired-session branch should expose its redirect state as a status or
  alert rather than relying on visual text alone.
- Recommended regression test: render every shared fallback in isolation and
  assert one status node with bounded loading/redirect text. Ensure skeleton
  rectangles are not emitted as individual announcements.

### 2. Admin time-range controls use a low-contrast pointer-focus indicator

- Status: OPEN
- Priority: MEDIUM
- Area: Admin telemetry time-range and refresh controls
- Rules: R-32 and the `antislop-human` focus-indicator/non-text-contrast
  guidance
- Evidence:
  - `console/src/features/admin/admin-time-range.tsx:319-324` and
    `:328-333` use `outline-none focus:border-smoke` for the custom `From`
    and `To` datetime controls.
  - `console/src/features/admin/admin-time-range.tsx:351-357` uses the same
    focus treatment for the refresh select.
  - The declared `smoke` token is `#383b3f` in
    `console/src/app/globals.css:25`, while the affected controls use
    `void` (`#08090a`) or `carbon` (`#0f1011`) backgrounds.
  - The required contrast checker reports `#383b3f` against `#08090a` as
    `1.77:1` and against `#0f1011` as `1.69:1`, both below the 3:1 minimum
    for a non-text focus indicator.
  - The global `:focus-visible` acid-lime outline provides a keyboard-focus
    fallback, but the explicit pointer-focus state remains a barely visible
    one-pixel border change and the component declares `outline-none`.
- Minimal proof path: open any Admin telemetry view, focus the custom range
  inputs or Refresh select with a pointer, and compare the focused border to
  its adjacent background. The border change is below the checked 3:1
  threshold and is easy to miss against the dark surface.
- Impact: users who click into these controls can lose the visual indication
  of which control is active. This is particularly risky in a dense telemetry
  toolbar where the current range and refresh settings affect all charts and
  tables below it.
- Recommended remediation: use the same acid-lime focus ring/border contract
  as the shared `Input` and `Textarea` primitives, preferably with
  `focus-visible` semantics and a checked 3:1 boundary against both `void`
  and `carbon`. Keep the dark visual language and do not introduce a new
  accent.
- Recommended regression test: render the three controls, inspect their
  focused styles in the dark theme, and assert the focus treatment uses the
  approved high-contrast accent rather than `smoke`.

### 3. Authentication and confirmation errors are not consistently announced

- Status: OPEN
- Priority: MEDIUM
- Area: authentication forms and shared destructive confirmation dialog
- Rules: R-27, C-4; current Vercel async-update and form-error guidance
- Evidence:
  - `console/src/features/auth/login-view.tsx:101-105` and
    `console/src/features/auth/register-view.tsx:89-93` insert mutation
    failures as ordinary paragraphs without `role="alert"` or a live
    region.
  - `console/src/features/auth/auth-flow-views.tsx:205-209` and
    `:260-264` do the same for password confirmation and recovery-request
    failures.
  - `console/src/components/confirm-dialog.tsx:48-52` renders an async
    confirmation failure as a plain paragraph after the dialog action fails.
  - The same repository already uses `ErrorState` and explicit
    `role="alert"` in many Admin mutation paths, so this is an inconsistent
    shared interaction contract rather than an intentional silent state.
- Minimal proof path: submit Login, Register, password recovery, password
  reset, or a failing ConfirmDialog action while focus remains on the submit
  or confirm button. The error is visible, but no bounded status/alert update
  is guaranteed to be announced to a screen reader.
- Impact: a user who cannot see the new red panel can miss why the operation
  did not complete and may repeat an action or assume the dialog closed.
  Authentication failures are especially important because the user has no
  other page state to explain the failed transition.
- Recommended remediation: add a shared, non-duplicating error presenter for
  async form/action failures with `role="alert"` (or a carefully scoped live
  status), and associate field-validation text with the relevant input via
  `aria-describedby`/`aria-invalid` where applicable. Preserve the current
  visible copy and privacy behavior.
- Recommended regression test: reject each mutation in component tests and
  assert the error is exposed through an alert/live region. For field errors,
  assert the invalid control references the rendered message.

### 4. The shared CreateDialog does not emit complete native form metadata

- Status: OPEN
- Priority: LOW
- Area: reusable create/edit dialog forms
- Rules: current Vercel form guidance; C-4 form usability
- Evidence:
  - `console/src/components/create-dialog.tsx:24-45` defines a field
    descriptor with a semantic `name`, but the name is used only as an
    element `id` and React state key.
  - `console/src/components/create-dialog.tsx:149-167` and `:223-233`
    render the textarea, select, and text inputs without a native `name`
    attribute. The descriptor has no `autoComplete` metadata either.
  - `console/src/components/create-dialog.tsx:194-210` renders multiselect
    checkboxes without a native name grouping.
  - Labels are present, so this is not a missing-label finding; it is a
    reusable form-semantics/autofill gap in a shared primitive.
- Minimal proof path: open a CreateDialog-backed form and inspect the form
  controls in the accessibility tree or submit it through native form
  serialization. The controls have IDs and labels but do not expose their
  field names to native form tooling, and appropriate browser autofill
  hints cannot be supplied by the field descriptor.
- Impact: browser autofill, password managers, extensions, and assistive
  tooling have less reliable field identification across the many dialogs
  built on this component. This is a lower-severity usability issue, not a
  claim that current React submission is broken.
- Recommended remediation: pass `name={field.name}` to each native control,
  add optional field-level `autoComplete` metadata for fields where the
  semantic token is known, and use a deliberate name/group strategy for
  multiselect checkboxes. Keep React state handling unchanged.
- Recommended regression test: render representative text, email, password,
  select, and multiselect fields; assert native names, labels, and supplied
  autocomplete values are present without changing submitted values.
