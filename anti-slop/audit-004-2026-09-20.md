# Anti-slop audit 004

Date: 2026-09-20
Mode: AFTER
Scope: Stealth Console frontend, with emphasis on shared navigation, admin
telemetry controls, responsive behavior, keyboard use, accessible semantics,
and state handling
Audited source: `634fda65359e8db459cdaf0459facafd97a88d3b`, incorporated into
main as `d7fa45a2e3dc8efc49a4ac966046346858d6bc14`

## Audit basis

This audit reapplied the installed `antislop`, `antislop-ui`,
`antislop-human`, and `antislop-layoutmobile` skills to the current Console.
It also used the repository's `DESIGN.md` files and current
[Vercel Web Interface Guidelines](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/command.md)
as the project-required UI and accessibility reference.

The review rechecked the findings resolved by audit 003, shared UI
primitives, navigation dialogs and the command palette, admin telemetry
screens, loading/error/empty states, responsive table containment, and
interactive semantics. No product source code was changed during this audit.

## Findings

### 1. Telemetry time-range choices are lost when browser storage is unavailable

- Priority: HIGH
- Rules: R-26 and C-4
- Rule rationale: a preference control must keep its chosen behavior during
  the active session even when optional browser persistence is unavailable.
- Evidence:
  - `console/src/features/admin/admin-time-range.tsx:44-88` made the
    selected range and refresh interval entirely dependent on reads from
    `localStorage`. A storage exception fell back to `1h` and `off`.
  - `console/src/features/admin/admin-time-range.tsx:142-162` caught a failed
    `setItem`, dispatched an event, but kept no in-memory preference.
  - `console/src/features/admin/admin-time-range.tsx:207-214` had the same
    problem for a custom range, which fell back to the default moving
    one-hour query.
  - `console/src/features/admin/admin-time-range.test.tsx` covered normal
    persistence and remounting, but did not make `getItem` or `setItem`
    throw.
- Reproduction: in a browser context where `localStorage.getItem` or
  `localStorage.setItem` throws, choose `24h`, a refresh interval, or a valid
  custom range on any Admin telemetry page. The displayed selection and query
  revert to the default rather than staying active for the current session.
- Impact: an operator can believe they are viewing a selected incident
  window while the API is queried for the default one-hour window. This is a
  control failure, not merely lost persistence across a reload.
- Suggested direction: own active range, refresh, and custom timestamps in
  React state. Treat `localStorage` as best-effort persistence and as a
  cross-tab input, never as the only live state source.
- Recommended regression test: make both storage reads and writes throw;
  verify preset, refresh, and valid custom selections remain rendered and
  produce the selected query for the current session.

### 2. Several operational controls are below the 44 px touch target

- Priority: HIGH
- Rule: R-03
- Rule rationale: a mobile operator must be able to activate every functional
  control with a reliable 44 px touch target.
- Evidence:
  - `console/src/features/admin/admin-time-range.tsx:221-234` rendered every
    range preset at approximately 24 px tall from `text-xs` plus `py-1`.
  - `console/src/features/admin/admin-time-range.tsx:241-260` fixed custom
    datetime fields and their Apply action at `h-8`, or 32 px. The refresh
    select was also explicitly `h-8`.
  - The same compact-control pattern was present in the log history select
    and the error status select.
- Reproduction: use the Admin telemetry controls on a touch phone. Adjacent
  presets, datetime fields, Apply, and Refresh are materially smaller than
  the Console's standard hit area.
- Impact: these controls occur in high-consequence operational workflows.
  The compact visual treatment turns ordinary touch selection into a
  precision task.
- Suggested direction: retain the compact visual language while giving each
  interactive control a 44 px hit box and responsive wrapping.
- Recommended regression test: add a mobile browser test that measures the
  rendered target dimensions for the shared time-range controls and verifies
  a wrapped layout still exposes all controls without clipping.

### 3. Infrastructure scope buttons claim tab semantics without implementing a tab interface

- Priority: HIGH
- Rule: R-32
- Rule rationale: stated control semantics and keyboard behavior must match
  the interaction users are given.
- Evidence:
  - `console/src/features/admin/admin-infrastructure-view.tsx:88-104` labelled
    the scope filter as `role="tablist"` and each native button as `role="tab"`
    with `aria-selected`.
  - The component did not render an associated `tabpanel`, provide
    `aria-controls`, or implement ArrowLeft/ArrowRight, Home, or End behavior.
    It only changed the `scope` filter for one metrics request.
- Reproduction: focus a scope choice and press the normal tab-list arrow keys.
  Focus and selection do not move. A screen reader is told this is a tab
  interface even though it is a set of query-scope filters with no panels.
- Impact: keyboard and assistive-technology users receive an interaction
  model that differs from the actual control.
- Suggested direction: either use a real tabs primitive with a connected
  panel and its expected keyboard model, or model this honestly as a
  segmented filter group using native buttons and `aria-pressed`.
- Recommended regression test: test the chosen semantic model and its query
  update behavior.

### 4. Virtualized Admin log rows override native button semantics and form an incomplete ARIA table

- Priority: HIGH
- Rule: R-32
- Rule rationale: a keyboard-focusable control must preserve a discernible
  action and its accessible structure.
- Evidence:
  - `console/src/features/admin/admin-logs-view.tsx:323-388` exposed the
    virtualized result as `role="table"`, then rendered each detail-opening
    native button as `role="row"`.
  - Applying `role="row"` replaced the button role exposed to assistive
    technology. The visual cells were plain spans rather than `cell` or
    `gridcell` roles, so the table lacked a complete row/cell structure.
  - The only detail action was the row click. The accessible name said
    `Open log from <service>`, but the element was announced as a row, not an
    action that could be opened.
- Reproduction: navigate the structured-log results with a screen reader.
  A result is exposed as a row instead of a button or an explicit row action,
  and its visible columns are not represented as accessible cells.
- Impact: the most detailed telemetry result view is difficult to understand
  and operate non-visually.
- Suggested direction: either preserve native button semantics and remove the
  table roles, or build a conformant grid/table with row and cell roles plus a
  separately named detail action.
- Recommended regression test: add an accessibility test for the selected
  structure and a keyboard test proving a log detail can be opened and closed
  with an announced, focusable control.

## Rechecked and passing areas

- Audit 003 findings remained addressed: detail views distinguish pending from
  completed not-found responses; navigation distinguishes loading, error, and
  empty states; log messages use a bounded viewport and break unbroken text;
  and mobile navigation uses the shared dialog with focus restoration and
  Escape support.
- R-02: no product-facing U+2014 punctuation was found in the Console source.
- R-17, R-18, R-36, and R-38: the reviewed product surfaces do not present
  fabricated metrics, testimonials, unsupported outcome claims, or false
  security claims.
- R-25: the Console's custom `slate-500` and `slate-600` aliases resolve to
  `#8a8f98`; the contrast checker reports 6.13:1 against `#08090a`.
- R-27: the reviewed Admin telemetry views show explicit pending, retryable
  error, and settled-empty states. The virtualized log table also bounds its
  list rather than rendering every record.

## Approval gate

All four findings were approved for remediation after this audit. The
corresponding resolution is recorded in the audit 004 follow-up document.
