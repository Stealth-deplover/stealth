# Anti-slop audit 002

Date: 2026-09-13
Mode: AFTER
Scope: Stealth Console frontend and shared UI primitives
Audited commit: `b5f9cb918d99e69501f2d573dbd88ce2c125b861`

## Audit basis

This follow-up audit applied the `antislop` core rules to the current Console
source, after the eight findings recorded in audit 001 were implemented. The
review covered the route tree, data views, shared controls, copy, color
tokens, icons, effects, responsive classes, keyboard behavior, and available
CI evidence. No product code was changed during this audit.

## Findings

### 1. Several data views show empty content while the first request is loading

- Priority: HIGH
- Rules: R-27 and C-4
- Evidence:
  - `console/src/features/organization/plan-view.tsx:14-31` handles errors
    and then renders `Plan unavailable` whenever `plan` is absent, without
    checking `query.isLoading` or rendering a loading indicator.
  - `console/src/features/deployments/deployments-view.tsx:23-81` renders
    `No functions on this page` and the equivalent Sites message while the
    corresponding query has no data yet. The queries' `isFetching` values are
    only passed to pagination controls.
  - `console/src/features/observability/logs-view.tsx:22-120` renders its
    `No log sources yet` state while either source query is still pending.
  - `console/src/features/messaging/messaging-view.tsx:19-139` renders
    `Not available` counts and `No topics returned` while the three initial
    queries are pending. It has no initial loading branch.
- Impact: Operators can be told that data is empty or unavailable before the
  API response arrives. This fails the required loading state and makes empty
  and loading states indistinguishable.
- Suggested direction: add explicit initial loading states for each view or
  each independently loading section, while preserving the current empty and
  error states and background pagination feedback.

### 2. The Account view becomes blank while the account query is pending

- Priority: HIGH
- Rules: R-27 and C-4
- Evidence: `console/src/features/account/account-view.tsx:25-53` starts the
  account query, handles an error, and then returns `null` whenever
  `account.data?.account` is absent. The sessions section has a loading label,
  but the primary identity surface has no loading or explicit unavailable
  state.
- Impact: A normal initial fetch produces a blank Account page with no
  progress signal, and an absent account response is not communicated to the
  user.
- Suggested direction: render the shared loading state while the account
  query is pending and an explicit empty/unavailable state if it completes
  without an account object.

### 3. Tab triggers do not meet the Console touch-target minimum

- Priority: HIGH
- Rules: R-03
- Evidence: `console/src/components/ui/tabs.tsx:23-26` defines every
  `TabsTrigger` with `px-3 py-2` and no `min-h-11`. The trigger is approximately
  34px high including its border. It is used by the Function, Bucket, Table,
  and Database detail views, for 13 tab controls in total.
- Impact: The main detail-view navigation is harder to operate on touch
  screens and does not meet the design direction's 44px interactive target.
- Suggested direction: give the shared tab trigger a 44px minimum height while
  retaining the compact visual treatment through alignment and padding.

### 4. A generic sparkle glyph is used without a documented product purpose

- Priority: MEDIUM
- Rules: R-04 and R-31
- Evidence: `console/src/components/navigation/context-switchers.tsx:9,294-298`
  renders `Sparkles` next to the `Live API context` label. `DESIGN.md`
  documents the palette and interaction direction but does not record why a
  sparkle is the relevant glyph for this operational context indicator.
- Impact: This reads as a generic decorative or AI-associated icon rather
  than a specific signal about the current API context.
- Suggested direction: use a context or connection glyph with a direct
  semantic relationship, or document a concrete reason for retaining the
  sparkle.

### 5. Resource canvas nodes use large elevation outside the documented overlay boundary

- Priority: MEDIUM
- Rules: R-12 and R-31
- Evidence: `console/src/features/services/services-canvas-view.tsx:90-95`
  applies `shadow-xl` to every resource node. `DESIGN.md` explicitly reserves
  elevation for overlays and transient layers, while the node is a persistent
  data element on the canvas. The selected-resource panel separately uses
  `shadow-2xl` as a transient overlay and is not part of this finding.
- Impact: Every canvas resource is made to float, and the implementation is
  inconsistent with the documented flat-panel elevation rule without a
  written node-specific rationale.
- Suggested direction: prefer the existing border and semantic surface
  treatment for nodes, or record and implement a narrowly scoped canvas
  separation rationale with a less dominant elevation.
